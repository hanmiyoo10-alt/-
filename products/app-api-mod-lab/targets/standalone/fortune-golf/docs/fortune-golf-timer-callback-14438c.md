# Probe 6 타이머 콜백 추적

## 실행 증거

사용자 스크린샷: timer=0x0016fde0, callback/target=0x0014438d, param=0, args=[0x16fde0,0], Invalid memory access address 4. 이 문맥은 콜백 실행 중 실패를 뜻하며 정확한 fault PC를 제공하지 않는다. 화면의 PC=0을 실제 실패 명령어 위치로 사용하지 않는다.

## 이번 분석 방법

fortune-ghidra-checkpoint.zip을 복구했다. 원본 client.bin SHA256: 4627f98a60dba7ed2cec6c9161ada1a834c247d6298e4d85fc6160657c1952ca. 이전 Ghidra 실행 파일은 현재 scratch에 없고 복구하지 못했다. 이번 명령어 검사는 설치된 libLLVM.so.20.1의 ARM disassembler (thumbv5-none-eabi)로 수행했다. 이번 결과를 새 Ghidra 디컴파일 성공으로 표현하지 않는다. 바이너리 및 전체 디스어셈블리는 공개 저장소에 올리지 않는다.

## 연결 확인

- Thumb 콜백 코드 시작은 0x14438c (함수 포인터의 bit 0 제거).
- PIC 테이블 기준 0x16b030. 테이블 +0x194의 파일 값 0x433ed에 기존 로더 기준 0x100fa0을 더하면 0x14438d.
- 테이블 +0x4c 값 0x6ee40에 같은 기준을 더하면 0x16fde0. 스크린샷의 타이머 주소와 일치한다.
- 0x101cf6–0x101d1c는 해당 타이머와 콜백을 준비하고 인터페이스 +100을 호출한 뒤, +104 호출에 시간 low=0x1388(5000), high=0, param=0을 전달한다. literal pool: 0x101d9c=0x4c, 0x101da0=0x194, 0x101da4=5000, 0x101da8=0.
- 기반 WIE 커널 테이블에서 +100/+104는 def_timer/set_timer와 일치한다. **param=0은 이 원본 호출 지점이 직접 설정한 값이다.** 0을 임의의 다른 값으로 고칠 근거가 없다.
- 콜백은 먼저 0x1015ac를 호출하고, 이후 테이블 +28의 함수로 r0=0을 전달한다. trampoline 0x15d3c4는 bx r3다.
- 0x1015ac는 전역에서 얻은 값을 0x1435e0에 두 번 전달한다. 0x1435e0은 입력 0을 건너뛰고 같은 테이블 +88을 호출한다. 기반 커널 테이블의 free(+88)/exit(+28)와 일치하므로 이 콜백이 정리 후 종료하는 경로라는 가설이 강해졌다. 런타임 테이블의 실값은 아직 캡처하지 않았다.

## 해석과 남은 작업

관찰한 콜백은 일반 프레임 갱신보다 정리/종료 경로에 가깝다. 최초 초기화 실패가 먼저 발생하고 종료 과정에서 별도 오류가 발생했을 가능성을 조사해야 한다. 원본이 이 분기로 들어오는 조건은 아직 미확정이다. 실제 주소 4 접근 명령어와 함수는 아직 특정하지 못했다. 타이머 취소 stub이나 RGB565가 원인이라고 단정하지 않는다.

다음 대상: 0x101cf6으로 들어오는 분기 조건과 0x1015ac 내부 간접 호출의 실제 대상. 필요하면 ARM 코어가 오류 시 레지스터를 복원하기 전에 fault PC와 호출 문맥을 보존해야 한다. 이번 작업에서는 APK 변경/빌드를 하지 않았다.
