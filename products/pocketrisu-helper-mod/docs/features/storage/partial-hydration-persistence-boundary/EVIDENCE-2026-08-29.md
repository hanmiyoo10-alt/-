This independently reinforces the existing dossier rule: **missing/unloaded/omitted state is not deletion; destructive intent must be explicit unless a caller has separately proven a complete authoritative replacement.**

## Design implications

Strengthen the proposed mechanism with these requirements:

1. Any delete derived from absence must require a typed/proven `COMPLETE_REPLACEMENT` capability; ordinary partial/delta/projection payloads may never infer deletion from omission.
2. Prefer explicit delete IDs/operations for user-authored durable entities when incremental commits are supported.
3. Keep `replaceAll`/restore/import replacement semantics separate from incremental commit semantics; do not overload a single manifest field to mean both projection membership and destructive authority.
4. Validate delete IDs at the protocol/write boundary and make deletion idempotent where practical.
5. If client and server versions disagree about explicit-delete support, fail closed or preserve stale data rather than falling back to complement pruning.

## Validation additions

Before any implementation, add to the PocketRisu audit matrix:

- partial payload omits an existing character/chat/entity -> persisted entity survives;
- explicit delete names that entity -> exactly that entity is removed;
- authoritative complete empty collection -> emptiness persists only through an explicit complete-replacement/delete contract;
- stale/failed hydration cannot generate deletes from absent fields;
- retrying the same explicit delete does not remove unrelated entities;
- client/server capability mismatch cannot silently reinterpret omission as deletion;
- replace-all remains independently tested, with rollback/backup expectations documented.
